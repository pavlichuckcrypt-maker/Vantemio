Revision 0.14 · 7 October 2026 · Editorial material and documentation history

## Documentation changes

This revision makes official Vantemio media production the first scenario. The official YouTube connection with automated publishing is recorded; acceptance defines repeatable-outcome requirements. External generation is conditional, the savings metric is narrowed, and API access, publication and monetization are distinguished.

An integration map, editorial review rules and a licence-clearance register have been added. Terms and Privacy reflect an Alberta-based individual operator, a 90-day application period and mandatory commercial clearance. Text changes do not establish completed connectors, data cleanup or legal review.

This is documentation change history. Revisions 0.9–0.12 established the package, TikTok rules and Home description; revision 0.14 clarifies API-data deletion, temporary uploads and local-delivery boundaries. Publishing these documents is not a new engine release.

## Editorial article: why one core matters

Category: architecture. Status: explanatory article; not a release announcement.

When tools retain only their own fragments, recovering the overall picture after an error becomes difficult. The Station core should connect the brief, versions, executor assignment and accepted result. Adding a compute node expands resources while retaining one control centre.

For a user, this answers practical questions: which version was accepted, which materials were used and why a revision was needed. An individually working tool does not establish end-to-end reliability. Evidence should therefore describe a completed scenario.

## Editorial article: when a video is ready

Category: Studio. Status: explanatory article; not a release report.

A file's existence, successful rendering, editorial acceptance and publication are separate events. Accepted video should meet the brief, use materials appropriately and pass visual and audio review. Publication additionally requires an authorized destination and confirmed platform state.

A useful revision identifies the defect and what should remain unchanged. The new version is linked to that finding, followed by verification of the actual correction. This supports quality assessment without pretending that one automated score replaces an editor.

## Future release reporting

Each release report identifies date, version, concrete change, supporting scenario and limits. An explanatory article is not labelled as a completed feature. Plans, experiments, documentation corrections and production releases are explicitly distinguished.
